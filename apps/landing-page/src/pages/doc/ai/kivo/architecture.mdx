# Kivo Architecture

Kivo Gateway is the runtime. Kivo Studio is the AI-agent creation environment. Kivo SDK is the downloadable integration layer. Power Totem is the functional hackathon template. Other templates are roadmap or marketplace candidates.

Kivo is organized around one primitive:

```txt
resource -> policy -> x402 requirement -> Stellar proof -> Etherfuse context -> Kivo authorization -> Gateway release -> receipt and health
```

The gateway can be physical or digital. Physical gateways run near hardware such as Raspberry Pi, totems, kiosks, or edge boxes. Digital gateways run as middleware, serverless functions, workers, reverse proxies, sidecars, queue consumers, or agent tool guards.

---

## Runtime Layers

| Layer | Role |
|---|---|
| Resource | The physical or digital thing being protected. |
| Policy | Price, asset, duration, scope, and release conditions. |
| x402 requirement | The payment challenge returned before access is granted. |
| Stellar proof | The settlement proof Kivo validates before authorization. |
| Etherfuse context | Visible anchor/funding context around the asset used in the flow. |
| Kivo authorization | A short-lived permission the gateway can enforce. |
| Gateway release | The physical or digital action performed after authorization. |
| Receipt and health | Events that prove release, completion, status, and operational health. |

---

## Physical Gateways

Physical gateways run close to hardware. The hackathon example is Power Totem: a Raspberry Pi or similar controller shows a QR checkout, waits for Kivo authorization, then releases a safe load for a short session.

Physical gateways should never release a resource because Etherfuse exists or because a client claims payment. They release only after Kivo validates the x402 payment state, Stellar proof, and policy conditions.

---

## Digital Gateways

Digital gateways protect APIs, workers, automations, proxies, sidecars, queue consumers, and agent tools. They enforce the same authorization model as physical gateways, but the release action is digital: forward a request, return data, trigger a workflow, execute a tool, or start a compute job.

Digital gateway adapters are part of the post-hackathon roadmap.

---

## Product Components

| Component | Responsibility |
|---|---|
| Kivo Gateway | Enforces authorization and emits gateway events. |
| Kivo Studio | Uses AI agents to help users design, configure, test, and publish flows. |
| Kivo SDK | Provides TypeScript helpers for resources, policies, x402, authorizations, webhooks, and gateway pairing. |
| x402 | Describes the paid access requirement. |
| Stellar | Provides settlement proof. |
| Etherfuse | Gives visible anchor/funding context. |
| Private mainnet billing | Lets validated flows stay private in production. |

---

## Studio-Led Build Path

Studio turns user intent into a flow, validation run, launch checklist, and SDK export. Gateway remains the runtime for physical or digital release, while SDK gives technical users a direct integration path for clients, adapters, examples, and tests.

Validated testnet flows must show real x402 and Etherfuse states. Private mainnet publication is a paid path; public templates remain the fallback for users who do not pay for private mainnet usage.
