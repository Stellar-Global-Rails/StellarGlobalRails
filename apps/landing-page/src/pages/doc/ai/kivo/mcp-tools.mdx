# Studio Agent Tools

Kivo Studio uses AI-agent-assisted tooling to help builders describe a resource, choose a physical or digital gateway, validate x402/Stellar/Etherfuse states, and prepare launch options. Kivo Gateway remains the runtime, and Kivo SDK is the local TypeScript integration layer.

The current Supabase Edge MCP surface is intentionally small. `GET /v1/mcp/tools` lists only:

| Tool | Current status | Safe for auto-use |
|---|---|---|
| `kivo_create_payment` | Current | No - requires payment approval policy |
| `kivo_check_status` | Current | Yes - read-only status check |
| `kivo_execute_contract` | Planned | No - future conditional execution tool |
| `kivo_subscribe_webhook` | Planned | No - future webhook management tool |
| `kivo_simulate_payment` | Planned | Yes, when implemented as testnet-only |

`kivo_execute_contract`, `kivo_subscribe_webhook`, and `kivo_simulate_payment` are roadmap tools. They are not currently exposed by `GET /v1/mcp/tools` or `GET /v1/mcp/config`.

---

## Current Edge MCP Routes

| Endpoint | Auth | Purpose |
|---|---|---|
| `GET /v1/mcp/tools` | Supabase JWT | Lists current MCP tool metadata |
| `GET /v1/mcp/config` | Supabase JWT | Returns HTTP MCP server config and approval policy |
| `POST /mcp` | Supabase JWT | Accepts JSON-RPC tool calls |

The current Edge implementation returns lightweight MCP responses. It is suitable for Studio demos and agent integration scaffolding; richer tool execution remains roadmap work.

---

## Current Tool: `kivo_create_payment`

Creates a Kivo payment intent for a device or x402 flow.

```json
{
  "id": "tool_create",
  "name": "kivo_create_payment",
  "title": "Create payment",
  "description": "Create a Kivo payment intent for a device or x402 flow.",
  "safeForAutoUse": false,
  "inputSchema": { "type": "object" },
  "exampleInput": { "amount": "0.0500000" }
}
```

Security posture:

- Requires a Supabase-authenticated user.
- Must be governed by a payment approval policy.
- Should require human confirmation above the configured amount threshold.

---

## Current Tool: `kivo_check_status`

Checks payment or device status.

```json
{
  "id": "tool_status",
  "name": "kivo_check_status",
  "title": "Check status",
  "description": "Check payment or device status.",
  "safeForAutoUse": true,
  "inputSchema": { "type": "object" },
  "exampleInput": { "paymentId": "pay_<id>" }
}
```

Security posture:

- Requires a Supabase-authenticated user.
- Read-only and safe for automatic agent use.
- Should still be scoped to the current user/workspace through Supabase ownership checks.

## Planned MCP Tools

These tools remain product direction, not current Edge API surface:

| Planned tool | Intended purpose |
|---|---|
| `kivo_execute_contract` | Submit condition proof or execute a future conditional settlement path |
| `kivo_subscribe_webhook` | Register or manage webhook delivery from an agent workflow |
| `kivo_simulate_payment` | Run a testnet-only simulated payment for agent development |

When these tools are implemented, this page should be updated from "planned" to "current" only after they appear in `GET /v1/mcp/tools`.

---

## Example Agent Flow

```txt
1. Agent encounters a Kivo-protected resource.
2. Agent inspects price, asset, nonce, and resource metadata.
3. Agent calls kivo_create_payment only if the amount is within policy.
4. Kivo validates x402/Stellar state through the Edge API.
5. Agent calls kivo_check_status to observe settlement or authorization state.
6. Gateway releases the protected physical or digital resource after Kivo authorization.
```

## Security Scoping

| Capability | Current auth | Notes |
|---|---|---|
| List tools | Supabase JWT | `GET /v1/mcp/tools` |
| Read MCP config | Supabase JWT | `GET /v1/mcp/config` |
| Call MCP tool | Supabase JWT | `POST /mcp` |
| Create payment | Supabase JWT + approval policy | Current tool, not safe for blind auto-use |
| Check status | Supabase JWT | Current read-only tool |
| Execute contract | Future | Do not configure as current |
| Subscribe webhook | Future | Do not configure as current |
| Simulate payment | Future | Do not configure as current |

Agents should be configured with a maximum automatic payment amount and a human confirmation requirement above that limit. Private mainnet usage is a paid path; public templates remain the fallback for users who do not publish privately.
