# API Reference

Kivo exposes a REST API through the Supabase Edge Function `kivo-api` and a Model Context Protocol (MCP) surface for AI agent integration. Authenticated dashboard, Studio, and SDK calls use a Supabase Auth JWT (`Authorization: Bearer <token>`). Gateway calls use `x-gateway-token`, and x402 resource unlocks use `X-PAYMENT`.

Kivo Gateway is the runtime. Kivo Studio is the AI-agent creation environment. Kivo SDK is the downloadable integration layer. Power Totem is the functional hackathon template. Other templates are roadmap or marketplace candidates.

**Base URL:** `https://<project-ref>.supabase.co/functions/v1/kivo-api` (production) | `http://127.0.0.1:54321/functions/v1/kivo-api` (local Supabase)

---

## Resource Model

Kivo APIs should be read through four core objects:

- `resource`: the physical or digital thing being protected, such as a power totem, API route, automation, sidecar, queue consumer, or agent tool;
- `policy`: the price, asset, duration, scope, and access conditions attached to that resource;
- `authorization`: the short-lived permission Kivo issues after settlement proof and policy checks pass;
- `gateway_event`: the runtime audit trail emitted by a physical or digital gateway as it requests, releases, completes, fails, or revokes access.

These objects sit on top of the existing device, payment, webhook, Etherfuse, and MCP endpoints below. The current REST contract still exposes the lower-level payment primitives, while the Kivo payment engine treats them as the implementation path for resource access.

## Authentication

| Endpoint Type | Header | Value |
|---|---|---|
| Dashboard, Studio, SDK endpoints | `Authorization` | `Bearer <supabase_jwt>` |
| Gateway endpoints | `x-gateway-token` | One-time paired gateway token |
| x402 endpoints | `X-PAYMENT` | Encoded Stellar payment proof |

## Endpoints

### Studio routes

Studio routes are the AI-agent creation path. They turn user intent into a flow, validation run, and launch checklist.

| Endpoint | Auth | Purpose |
|---|---|---|
| `POST /v1/studio/intents` | Dashboard JWT | Parse user intent into Studio surface, interaction model, and recommended Gateway mode |
| `POST /v1/studio/flows` | Dashboard JWT | Create a Studio flow from an intent or prompt |
| `POST /v1/studio/flows/:flowId/validation-runs` | Dashboard JWT | Start testnet validation for a flow |
| `GET /v1/studio/flows/:flowId/launch-options` | Dashboard JWT | Return launch options for validated or pending flows |
| `GET /v1/studio/templates` | Public | List Studio templates; only Power Totem is functional for the hackathon |

Future Studio API candidates include validation-run detail lookup, gateway-mode updates, and SDK export downloads. They are not current Edge routes.

### Power Totem and Gateway routes

Power Totem is the functional hackathon template. The Gateway runtime releases the resource only after Kivo validates the x402 payment state, Stellar settlement proof, Etherfuse context, and policy conditions.

| Endpoint | Auth | Purpose |
|---|---|---|
| `GET /v1/power-totems` | Dashboard JWT | List Power Totems |
| `POST /v1/power-totems` | Dashboard JWT | Create a Power Totem |
| `GET /v1/power-totems/:id` | Dashboard JWT | Fetch one Power Totem |
| `POST /v1/power-totems/:id/pairing-token` | Dashboard JWT | Create the one-time gateway pairing token |
| `GET /v1/power-sessions` | Dashboard JWT | List Power Sessions |
| `POST /v1/power-sessions` | Dashboard JWT | Create a Power Session |
| `POST /v1/power-sessions/:id/start-checkout` | Dashboard JWT | Create the x402 challenge for `/power-totem/{id}/session` |
| `POST /v1/power-sessions/:id/authorize` | Dashboard JWT | Authorize a Power Session after validation |
| `POST /v1/power-sessions/:id/complete` | Dashboard JWT | Complete a Power Session |
| `POST /v1/gateways/:id/heartbeat` | `x-gateway-token` | Report gateway health |
| `GET /v1/gateways/:id/authorization` | `x-gateway-token` | Fetch short-lived authorization |
| `POST /v1/gateways/:id/events` | `x-gateway-token` | Report release, completion, failure, or revocation events |
| `GET /power-totem/{id}/session` | `X-PAYMENT` | x402-protected Power Totem resource |

Create a new payment record for the authenticated dashboard user. The Edge API expects explicit `fromDeviceId`, `toDeviceId`, `amount`, `assetCode`, `conditionType`, and optional condition/timeout/memo fields.

### `GET /v1/health`

Health check for the current Supabase Edge runtime. It reports API/runtime state, Supabase configuration, Stellar status, MCP surface status, and version. Etherfuse configuration is exposed through `GET /v1/etherfuse/status`, while gateway health is visible through heartbeat, authorization, session, and deploy-status routes. Redis workers are not part of the active Edge MVP runtime.

**Response `200`:**
```json
{
  "api": "ok",
  "db": "ok",
  "stellar": "ok",
  "mcp": "degraded",
  "version": "kivo-edge-transition-2026-05-17"
}
```

---

### `GET /api/x402/data`

Example of an x402-protected premium data endpoint. Returns 402 if no payment header is present.

**Response `402` (no payment):**
```
HTTP/1.1 402 Payment Required
X-PAYMENT-REQUIRED: scheme=stellar,network=testnet,payTo=GDQP2KPQ...,amount=0.1,asset=USDC,maxTimeout=300
```

**Response `200` (valid payment header):**
```json
{ "data": "premium sensor reading", "timestamp": "..." }
```

## Etherfuse Anchor Endpoints

Kivo exposes Etherfuse through its own backend so browser clients never receive anchor credentials. See [Etherfuse Integration](/doc/ai/kivo/etherfuse-integration) for the full sandbox/testnet runbook, schemas, webhook verification, and production checklist.

| Endpoint | Auth | Purpose |
|---|---|---|
| `GET /v1/etherfuse/status` | Dashboard JWT | Show whether the sandbox/production anchor is configured |
| `POST /v1/etherfuse/onboarding-url` | Dashboard JWT | Create hosted onboarding URL for a Kivo operator/customer |
| `GET /v1/etherfuse/assets` | Dashboard JWT | Discover Stellar rampable assets for a wallet |
| `POST /v1/etherfuse/quotes` | Dashboard JWT | Create onramp/offramp/swap quote |
| `POST /v1/etherfuse/orders` | Dashboard JWT | Create ramp order from a quote |
| `GET /v1/etherfuse/orders/:id` | Dashboard JWT | Poll order state as fallback to webhooks |
| `POST /v1/etherfuse/orders/:id/fiat-received` | Dashboard JWT, sandbox only | Advance sandbox onramp demo |
| `POST /v1/etherfuse/webhook` | `X-Signature` | Receive signed Etherfuse events |

The upstream Etherfuse API expects `Authorization: <api-key>` directly, with no `Bearer` prefix. Kivo stores that key server-side and maps Etherfuse order states into Kivo provider states for the dashboard.

## MCP Tools Specification

The current Edge MCP surface lists two tools from `GET /v1/mcp/tools` and includes those same names in `GET /v1/mcp/config`. See [MCP Tools](/doc/ai/kivo/mcp-tools) for broader integration notes.

### `kivo_create_payment`

Create a Kivo payment intent for a device or x402 flow. This tool is not safe for automatic use without human approval.

```json
{
  "id": "tool_create",
  "name": "kivo_create_payment",
  "title": "Create payment",
  "description": "Create a Kivo payment intent for a device or x402 flow.",
  "safeForAutoUse": false,
  "inputSchema": { "type": "object" },
  "exampleInput": { "amount": "0.0500000" }
}
```

### `kivo_check_status`

Check payment or device status. This tool is marked safe for automatic use.

```json
{
  "id": "tool_status",
  "name": "kivo_check_status",
  "title": "Check status",
  "description": "Check payment or device status.",
  "safeForAutoUse": true,
  "inputSchema": { "type": "object" },
  "exampleInput": { "paymentId": "pay_<id>" }
}
```

The current JSON-RPC response for `POST /mcp` is a lightweight Edge response:

```json
{
  "jsonrpc": "2.0",
  "id": "request-id",
  "result": {
    "content": [{ "type": "text", "text": "{\"status\":\"ok\"}" }],
    "isError": false
  }
}
```

## TypeScript MCP Client Example

```typescript
// AI agent using Kivo MCP tools (Claude / any MCP-compatible agent)

import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic();

// The agent autonomously charges an EV by calling Kivo tools
const response = await client.messages.create({
  model: "claude-opus-4-5",
  max_tokens: 1024,
  tools: [
    // Kivo MCP tools are registered in claude_desktop_config.json
    // and injected automatically — no manual tool definitions needed
  ],
  messages: [
    {
      role: "user",
      content: `
        The EV at charger station A12 (device ID: d5e3f1a2-...) 
        needs 10 kWh. The car's device ID is a1b2c3d4-...
        USDC rate: $0.30 per kWh. Set a 2-hour timeout.
        Create the payment and confirm when it is settled.
      `,
    },
  ],
});
```

## Error Responses

All error responses follow a consistent shape:

```json
{
  "error": "machine_readable_code",
  "message": "Human-readable message.",
  "status": 400
}
```

| HTTP Status | Example `error` | Meaning |
|---|---|---|
| 400 | `invalid_device`, `missing_xdr` | Malformed body or invalid parameters |
| 401 | `gateway_token_required`, `gateway_unauthorized` | Missing or invalid dashboard JWT, gateway token, or payment proof |
| 402 | `payment_required` | x402 endpoint payment header required |
| 403 | `gateway_suspended` | Valid auth but insufficient scope or suspended access |
| 404 | `not_found`, `payment_not_found` | Resource or route not found |
| 409 | `payment_already_confirmed` | Resource state conflict |
| 410 | `nonce_expired` | x402 nonce expired or no longer usable |
| 500 | `internal_error` | Server error |
| 503 | `etherfuse_not_configured`, `x402_platform_key_missing` | Required provider or runtime secret is not configured |
