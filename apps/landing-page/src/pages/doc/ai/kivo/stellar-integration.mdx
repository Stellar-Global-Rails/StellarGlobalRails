# Stellar Integration

Kivo uses Stellar as the settlement proof layer for x402 and Gateway authorization. The current implementation runs in the Supabase Edge Function `kivo-api`, where signed Stellar XDR is validated and submitted server-side.

Go Stellar SDK setup and Redis webhook queue examples were part of an older backend plan. They are retired for the MVP unless explicitly revived as a future dedicated worker path.

---

## Current Runtime

| Concern | Current path |
|---|---|
| API runtime | Supabase Edge Function `kivo-api` |
| Horizon network | `STELLAR_HORIZON_URL` |
| Network selection | `STELLAR_NETWORK=testnet` or `mainnet` |
| x402 recipient | `X402_PLATFORM_KEY` |
| USDC issuer | `USDC_ISSUER` |
| Payment proof | Signed Stellar `txXDR` |
| State persistence | Supabase Postgres |

The browser or wallet produces signed XDR. The Edge Function validates the transaction against the expected nonce memo, destination, amount, and asset before submitting to Horizon.

---

## Current Payment Flow

```txt
1. Kivo creates an x402 challenge.
2. User wallet or SDK signs a Stellar transaction XDR.
3. Client submits `{ nonce, txXDR }` to `POST /v1/x402/pay`.
4. Edge validates nonce memo, destination, amount, asset, and network.
5. Edge submits signed XDR to Horizon.
6. Edge records Stellar hash/ledger and updates Kivo payment/session state.
7. Gateway receives authorization and releases the resource.
```

Power Totem uses this flow to prove a real-world resource can be released after verifiable payment.

## Environment

```txt
STELLAR_NETWORK=testnet
STELLAR_HORIZON_URL=https://horizon-testnet.stellar.org
X402_PLATFORM_KEY=G...
USDC_ISSUER=GBBD47IF6LWK7P7MDEVSCWR7DPUWV3NY3DTQEVFL4NAT4AQH3ZLLFLA5
```

`X402_PLATFORM_KEY` must be a funded Stellar public key. Secret keys must not be committed or exposed to the browser.

---

## x402 Validation

The signed transaction must:

1. Pay the expected destination.
2. Pay the expected amount.
3. Use the expected asset.
4. Include the x402 nonce as memo.
5. Be valid for the configured Stellar network.
6. Submit successfully to Horizon.

Errors use the current Edge shape:

```json
{
  "error": "x402_payment_mismatch",
  "message": "Signed transaction does not match the x402 challenge.",
  "status": 400
}
```

---

## Etherfuse Relationship

Etherfuse does not process x402. Etherfuse provides funding/anchor visibility around Stellar assets. Kivo still validates and authorizes resource access.

```txt
Etherfuse funding context -> Stellar wallet balance -> x402 payment -> Kivo authorization -> Gateway release
```

## Future Worker Path

At higher volume, Kivo may add durable workers for:

- Settlement retries.
- Webhook fanout.
- Reconciliation exports.
- Rate limiting and replay protection at scale.

Redis, queues, and Go/Rust signing services belong in that future worker discussion. They are not the current MVP runtime.

## Common Stellar Errors

| Error | Cause | Resolution |
|---|---|---|
| `op_no_destination` | Recipient account does not exist | Fund destination or use a valid Stellar account |
| `op_underfunded` | Source lacks balance | Fund wallet through Friendbot/Etherfuse/manual transfer |
| `tx_too_late` | Transaction timebounds expired | Rebuild and re-sign XDR |
| `op_no_trust` | Missing trustline for issued asset | Add the required trustline |
| `tx_bad_seq` | Sequence number mismatch | Re-fetch account and sign fresh transaction |
| `tx_insufficient_fee` | Fee too low | Rebuild with appropriate fee |

For demos, keep the Stellar path on testnet unless private mainnet publication has been explicitly enabled.
