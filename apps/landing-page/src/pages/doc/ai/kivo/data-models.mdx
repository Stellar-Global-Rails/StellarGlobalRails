# Data Models

Kivo stores product state in Supabase Postgres and exposes it through the Supabase Edge Function `kivo-api`. The current model is Gateway-core + Studio-led: Studio creates flows and validation state, Gateway enforces authorization, and the TypeScript client contracts define the browser-facing shape.

Go/sqlc structs, Go backend query examples, and Stellar monitor goroutines were part of a retired implementation plan. They are not the current MVP data access path.

---

## Current Shape

```txt
auth.users
  -> kivo_devices
  -> kivo_payments
  -> kivo_payment_conditions
  -> kivo_power_totems
  -> kivo_gateways
  -> kivo_power_sessions
  -> kivo_gateway_events
  -> kivo_webhooks
  -> kivo_webhook_deliveries
  -> kivo_api_keys
  -> kivo_x402_nonces / pricing state
  -> kivo_etherfuse_webhook_events
```

The Edge Function maps database rows into camelCase TypeScript contracts used by `apps/kivo/web/src/types/kivo.ts`.

## Core Contracts

### Devices

Frontend contract:

```ts
interface Device {
  id: string;
  name: string;
  ownerId: string;
  apiKeyPreview: string;
  stellarPublicKey: string;
  status: 'active' | 'suspended' | 'decommissioned';
  metadata: Record<string, string>;
  balances: Array<{ assetCode: 'USDC' | 'XLM'; amount: string }>;
  createdAt: string;
  updatedAt: string;
}
```

Device rows are dashboard-owned. The browser receives key previews and one-time raw API keys only when created; server-side hashes and secrets must never be returned.

### Payments

```ts
interface Payment {
  id: string;
  fromDeviceId: string;
  toDeviceId: string;
  amount: string;
  assetCode: 'USDC' | 'XLM';
  assetIssuer?: string;
  conditionType: 'none' | 'energy_kwh' | 'time_elapsed' | 'service_complete' | 'custom';
  conditionValue?: string;
  status: 'pending' | 'processing' | 'confirmed' | 'failed' | 'expired' | 'refunded';
  stellarHash?: string;
  stellarLedger?: number;
  memo?: string;
  timeoutAt?: string;
  createdAt: string;
  confirmedAt?: string;
  failedReason?: string;
  feeCharged?: string;
}
```

Payments are created and updated through `kivo-api`. Signed Stellar XDR validation/submission happens server-side in the Edge Function.

### Power Totem

```ts
interface PowerTotem {
  id: string;
  name: string;
  resource: string;
  price: string;
  unit: 'session' | 'minute' | 'kWh';
  sessionDurationSeconds: number;
  status: 'draft' | 'pairing' | 'testing' | 'active' | 'paused' | 'failed';
  qrSlug: string;
  metadata: Record<string, unknown>;
  createdAt: string;
  updatedAt: string;
}
```

Power Totem is the only functional hackathon template. Other templates are roadmap or marketplace candidates.

### Gateway Runtime

```ts
interface Gateway {
  id: string;
  totemId?: string | null;
  name: string;
  tokenPreview: string;
  pairingTokenPreview?: string | null;
  status: 'pairing' | 'online' | 'offline' | 'suspended';
  adapter: 'simulator' | 'raspberry';
  lastSeenAt?: string | null;
}
```

Gateway routes use `x-gateway-token`. Gateway tokens are hashed server-side and only preview values are returned after creation.

### Power Sessions

```ts
interface PowerSession {
  id: string;
  totemId: string;
  gatewayId?: string | null;
  paymentId?: string | null;

```

Power Sessions bridge x402 payment state to Gateway authorization.

## Studio Contracts

Current Studio Edge routes support intent capture, flow creation, validation runs, launch options, and templates.

```ts
interface StudioIntent {
  id: string;
  prompt: string;
  surface: 'physical' | 'digital' | 'hybrid';
  interactionModel: 'H2M' | 'M2M' | 'A2M' | 'mixed';

  createdAt: string;
}

interface StudioFlow {
  id: string;
  intentId: string;
  name: string;
  surface: 'physical' | 'digital' | 'hybrid';
  interactionModel: 'H2M' | 'M2M' | 'A2M' | 'mixed';
  gatewayMode: string;
  resourceName: string;
  price: string;
  asset: string;
  accessRule: string;
  status: 'draft' | 'needs_setup' | 'validating' | 'validated' | 'ready_to_launch' | 'published';

```

Automated SDK export/download routes are future work. Today, Studio provides SDK/config guidance and a local TypeScript package path.

## RLS And Service Role Boundaries

Dashboard-facing tables must keep RLS enabled. User-scoped reads and writes should be constrained by `owner_id = auth.uid()` or equivalent ownership checks.

The Edge Function may use `SUPABASE_SERVICE_ROLE_KEY` for trusted server-side operations, including:

- Gateway token lookup by hash.
- x402 nonce/payment state transitions.
- Etherfuse webhook persistence.
- Power Session authorization transitions.

The service role key must never be exposed to Vercel or browser code.

## Edge Mapping Rules

| Database style | API/client style |
|---|---|
| `owner_id` | `ownerId` |
| `stellar_public_key` | `stellarPublicKey` |
| `api_key_preview` | `apiKeyPreview` |
| `created_at` | `createdAt` |
| `updated_at` | `updatedAt` |
| `x402_nonce` | `x402Nonce` |
| `gateway_id` | `gatewayId` |
| `totem_id` | `totemId` |

Keep snake_case inside Postgres and camelCase at the TypeScript boundary.
