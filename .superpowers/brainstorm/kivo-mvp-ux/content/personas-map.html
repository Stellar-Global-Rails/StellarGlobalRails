Personas do Kivo MVP

Um produto como o Kivo tem compradores, operadores, integradores e usuários finais. O MVP precisa escolher quem recebe a melhor experiência primeiro.

1

Operador de infraestrutura M2M

Dono de estação EV, rede IoT, marketplace de dados ou energia P2P. Usa o Kivo para cadastrar devices, acompanhar receita, ver pagamentos liquidados, status Stellar/Etherfuse e falhas operacionais.

2

Usuário final pagador

Pessoa, app ou agente que precisa consumir algo pago: carregar EV, comprar dados, rodar compute, acessar API ou liberar recurso x402. Quer pagar, entender preço/status e receber acesso imediatamente.

3

Integrador / builder / dev de agentes

Empresa ou dev que pluga o Kivo em produtos próprios. Usa templates, API keys, snippets, MCP tools, webhooks e x402 para implementar cobrança programável.

4

Financeiro / admin do negócio

Pessoa que não opera device nem integra API, mas precisa ver recebíveis, conciliação, volume, taxas, falhas, exportações e provas de liquidação.

Como cada uma usaria o Kivo

Fluxo principal B2B2C
Operador cria workspace e cadastra devices
Integrador conecta API/webhook/x402
Usuário final paga e desbloqueia uso
Financeiro acompanha receita e liquidação
Produto visto por cada persona
Operação | Cliente | Integração | Financeiro
Cada aba tem linguagem diferente, mas compartilha os mesmos payments/devices por baixo.
Valor de negócio
Prova técnica

Minha leitura

  • A persona compradora/operadora deve ser a principal do MVP.
  • O usuário final precisa existir como fluxo de prova, não necessariamente como app completo.
  • O integrador precisa de um caminho curto para provar API/x402/MCP.

Risco se não escolhermos

  • O app vira cockpit técnico demais.
  • A demo não mostra quem paga, quem recebe e por que isso importa.
